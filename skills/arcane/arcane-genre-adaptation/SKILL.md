# Design the requested game, then prove its loop

Use the actual brief, existing place and intended players to identify the primary play loop. A small repair should preserve the surrounding game. A complete-game request needs a connected experience: first arrival, understandable action, challenge, consequences, recovery, progression where appropriate and a reason to play again. A representative slice is an early milestone, not permission to call a starter map or a reskinned mechanic finished.

## Choose the design that changes decisions

Read the relevant entry in [genre profiles](references/genres.md); load that profile and the matching kit only. A hybrid names its primary loop and explains what each borrowed system contributes. Do not default to horror, forests, racing, loot boxes or combat when the user chose another experience. Preserve supplied references and identity without copying another game's assets, branding or maps.

Translate the brief into observable promises. For each, name the player action, authoritative state change, visible feedback, failure/retry and the content that exercises it. Identify dependencies: a reward needs a useful purchase; a key needs a reachable lock; a role needs an activity with another participant; a race needs handling and validated results. Build those links rather than unrelated impressive props. Resolve only missing decisions that would change the project substantially; use coherent stated assumptions for routine details.

## Grow from proof to actual breadth

Block out the riskiest interaction first, then play it before decorating every location. Once it works, extend it through authored situations that demand different choices: route shape, opponent behavior, puzzle rule combinations, production bottlenecks or social roles. Color swaps and larger health/currency numbers alone are weak variation. Set a content plan proportional to the request and available time; do not invent a universal map count. Record what is implemented versus still planned.

Compose systems with purpose. `arcane-rounds`, `arcane-inventory`, `arcane-economy`, `arcane-npc` and `arcane-combat` handle real state; `arcane-interface`, `arcane-rig-animation`, `arcane-vfx` and `arcane-audio` make it legible. Choose a consistent palette, scale, silhouette language and sound hierarchy for this game. Use original geometry appropriate to the brief; genuinely custom Blender work requires actual authoring/process capabilities and workspace permission. MCP-only capabilities are bounded; Toolbox is used only when requested. Never imply that a skill adds a missing tool, permission, native import or usable audio/animation asset ID.

## Build and review through the real surface

Inspect actual parents and source before edits. Use current `scene_build`/scene tools for supported data, exact `script_read` baselines for script changes, and review disabled scripts before enabling. Unknown write outcomes are read back rather than automatically repeated. Cross-link `arcane-playtest-qa`: `playtest_request` prepares a finite run for separate human approval; follow actual `playtest_status` through input release, owned stop and restoration. Do not approve it yourself or replace an unsupported action with invented evidence.

Acceptance must traverse the real flow with actual GUI, movement, rewards and failure, not just inspect scene names. Check a returning player, denied action, late join/disconnect if relevant, target-device layout and a repeated session for stale state/leaks. Separate source review, controlled fixtures, actual play, visual/audio review and untested multiplayer/persistence. Report the remaining content and quality gaps plainly. Technical success and these instructions cannot establish popularity, retention or universal realism.
