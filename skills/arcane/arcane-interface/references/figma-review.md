# Figma design, human review and Roblox implementation

## Establish access and scope
The intended product flow is Connect Figma in Arcane, browser sign-in to the user's Figma account, then creation of a new editable design file for the task. Do not require the user to prepare a file before starting. Offer an existing file only when the user wants to reuse one.

Use an actual connected Figma capability that can create or edit the user's permitted file. Reading a design, exporting an image and writing editable frames are different capabilities; verify which are available. Never invent a Figma tool or imply an export tool can author a file. Keep credentials in the supported connection flow. If connection or file creation is unavailable, retain the brief and report the unavailable stage. Do not call a screenshot a Figma document.

Figma's official remote MCP documentation currently describes `create_new_file` for file creation and `use_figma` for editable canvas work. It also restricts connection to supported clients, and canvas writing to eligible plans with edit access. Discover actual tools after authorization instead of assuming that documented tools are enabled for this account. A custom Arcane MCP client needs Figma acceptance; do not impersonate another client or silently route through unrelated credentials. Source: https://developers.figma.com/docs/figma-mcp-server/remote-server-installation/, https://developers.figma.com/docs/figma-mcp-server/tools-and-prompts/, https://developers.figma.com/docs/figma-mcp-server/write-to-canvas/. Recheck access terms when implementing.

Identify the game's audience, art direction, input devices and screen inventory. Read the user's existing design system. For an unspecified style, present a few relevant visual directions and choose with the user; do not force every game into a dark dashboard. Support playful/stud, illustrated fantasy, restrained modern, military/tactical, diegetic sci-fi, historical, horror, pixel and other requested directions through project-specific type, surfaces, shape language, imagery and motion. This is a design target, not a claim that all styles have passed evaluation.

The user's quality reference is https://builtbybit.com/resources/roblox/graphics-ui/. Treat it as a benchmark for coherent complete packs, readable HUDs, detailed menus and integrated feedback. Create original compositions and assets; marketplace listings do not grant rights to copy paid packs. Choose representative references for the requested style instead of averaging incompatible styles.

## Create a complete reviewable design
Build editable Figma frames, reusable components/variants, layout constraints and named design tokens. Include the actual required screens and their navigation, not only a showcase panel. Show hierarchy, realistic long labels/numbers and representative game content. Document palette roles, type sizes, spacing, icons, borders, shadows, focus, disabled/pending/error states and transitions. A shop needs purchase/insufficient-funds/processing/outcome states; a HUD needs legible objective and critical feedback. Apply only the screens the game needs.

Provide desktop and representative phone layouts, safe-area reservations, controller focus order and a clear back/close route. Inspect the actual frames for alignment, clipping, readable contrast, dense lists, localized text growth and touch targets. Prototype primary navigation and key transitions. Add appropriate motion/SFX intent without fabricating playable audio or claiming a prototype validates game logic.

## Review and approval
Present review inside Arcane: actual design previews, screen/state navigation, interaction explanation, feedback, revision history, Request changes and Approve design. Figma links are supplemental; do not require users to leave Arcane to inspect or approve. Clearly distinguish interactive prototypes from static previews and unavailable states. Ask the user to review visual direction, legibility, completeness and behavior. Record feedback as concrete changes and revise the same design; surface unresolved requests. Keep design work separate from game changes while approval is pending.

Approval must identify the file, relevant node IDs and exact version/revision when available. Retain a design snapshot/export digest and the user's decision with the task if Figma cannot expose an immutable revision. Re-read before import and compare the approved representation. Material changes to layout, typography, palette, imagery or navigation require review again. A generic "continue" on an unrelated task is not design approval. Do not claim a durable approval gate exists merely because these instructions describe one: use the product's actual supported review records and disclose a missing record capability.

## Translate the approved design
After approval, map each node/component to an editable Roblox GUI hierarchy and named controller bindings. Native layout, text and buttons remain GuiObjects; export appropriate original decorative vectors/illustrations as supported image assets. Do not flatten the full UI into one image. Preserve constraints, anchors, spacing, safe areas and text bounds rather than copying a single desktop frame's absolute pixels everywhere.

Produce an asset manifest with source node/version, export dimensions, transparency, role, digest, intended GUI node and eventual upload result. Fonts, gradients, clipping/masks, blend modes and effects may not map exactly; inspect actual Roblox support and show any material substitution for review. Use the authorized image import/upload path and retain its actual result. A local PNG or an asset job ID is not a successfully imported image. Explain the failed stage, cause and recovery when design fetch, export, upload, hierarchy creation or binding fails; preserve successful earlier stages without repeating uncertain writes.

Use the current scene.gui schemas for the editable static tree and reviewed scripts for behavior. Wire buttons to real systems, server-authoritative actions, pending/denied feedback and current state. Implement input-neutral Activated behavior, controller/touch navigation, focus restoration, animation cancellation, reduced motion and lifecycle cleanup. Include appropriate audio/VFX where the brief benefits, with the actual supported asset and playback paths. A decorative click animation does not establish a functioning purchase or inventory.

## Accept the actual result
Compare in-game captures with the approved design at agreed desktop and phone sizes, identifying intentional adaptations. Test navigation, primary actions, errors, empty/loading states, long text, repeated open/close, respawn and cleanup. Inspect the real PlayerGui; an Edit viewport or SurfaceGui presentation is insufficient. Keep visual comparison separate from interaction/state verification. Report what was actually imported and played, unresolved differences and unsupported checks. Never describe the whole Figma-to-game workflow as complete from a document, skill-pack test or screenshot alone.
