# Provider startup latency

The customer reports slow provider connection, slow selected-model loading and a new Error440 on every launch. The installedf8 app produced an original connect refusal after roughly50seconds. The physical closure cause of that original failure remains unproven; its custody/request is retained without review or retry.

## Measured cause and implementation

The desktop's standard Windows PATH selects a different installed Codex executable from the editor environment. Its separate metadata-only factory observation passed but took39.656seconds: about38seconds were spent on sequential inherited MCP tool-catalog pages, while the final account/model initialization took about1.3seconds. Disabling inherited plugins alone reduced the discovery workload but still took about22seconds. These are separate completed observations, not retries of the app request.

The production host now opts into configuration discovery. Its secret-free child disables inherited plugins and built-in apps, reads effective configured server names through config/read with includeLayers:false and the exact project directory, and retains only validated names. Arcane must be explicitly disabled and expose no tools in this discovery configuration. Invalid tables/names, excessive names, active Arcane, plugins or apps refuse before final authority. Only an explicit method-not-found response permits the existing full inventory compatibility path; malformed, timed-out and unknown replies do not trigger a fallback or replay.

The final native child and isolated history template use the same app/plugin fences and disable the inherited configured server names. Configuration declarations supply disable arguments only. They never certify runtime capabilities: actual thread MCP isolation, required Arcane tools, exact task ownership, workspace and asset admission remain mandatory before model work. No user configuration files are edited. Raw configuration values are not published in snapshots, events, diagnostic evidence or argv. A config/read frame refusal keeps its original error without attaching public frame evidence. The operational frame, server/tool, timeout and closure bounds are unchanged.

The new native path passed with the actual desktop-selected executable, saved subscription and eight models in about2.6seconds. A separate native asset-hook metadata observation also passed with one fresh unregistered final credential, no dispatch and exact original process/stream closure. The final app-and-plugin-disabled profile passed a further original observation after that source change, again about2.6seconds. Each child received one stdin end, no kill, exit0, both output EOFs and child close. No native thread, prompt, real Arcane daemon credential or Studio operation was created. These checks do not clear earlier failed custody or prove packaged customer Send.

The fixed configuration read and child plugin setting were checked against the [official app-server protocol](https://learn.chatgpt.com/docs/app-server) and [official plugin configuration documentation](https://developers.openai.com/plugins/build/plugins), and the exact installed executable's generated protocol types. The private schema generation completed once; no auth or model request was sent.

## Acceptance boundary

Strict660 compilation and294 frozen client/bootstrap/isolation/shutdown/browser cases passed before the final additional built-in-app fence. Final126-case guard/bootstrap/inventory/shutdown verification passes with frozen inputs, no skips and no cancellations. Packaged CI, installation and actual customer connection/Send remain outstanding. Claude connection speed is not established by these Codex measurements.
