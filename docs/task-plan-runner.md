# Bounded task plan runner

The host-only runner connects the [plan journal](task-plan-journal.md) to private worker, parent-continuation and evidence-request ports. It observes the original native terminal, requests three proposal roles in the first round and two in the second, and incorporates useful proposals through two original-parent turns. The existing task owner supplies the ports; there is no browser or MCP dispatch API.

Ordinary chat Send does not start this runner. It submits the new user message to the existing native conversation and leaves suggestions on request through **Ask for a proposal**. Short follow-ups therefore stay with the original conversation instead of becoming isolated worker prompts. The desktop hides the plan card when the server reports no plan; historical plan records remain readable. An embedding may explicitly opt into multi-round orchestration using the trusted `automaticTaskPlanning` service option (`codexAutomaticTaskPlanning` in the connection lab). HTTP and model input cannot enable that option. The standard desktop leaves it disabled.

The original objective is limited to 8 KiB for worker context. Its hash and the host's complete original-input hash are bound to the plan. Workers receive bounded context and return proposals only. Fan-in selects whole proposals in worker order within the journal's byte limit; it never truncates generated text. Callback envelopes reject proxies and accessors without evaluating them.

Both proposal and step reservations must succeed before a worker factory runs. A parent step needs its exact acknowledgement and then an observed terminal. Failed parents stop the plan. Unknown outcomes fence it without replacement attempts. After the second-round workers settle, the runner reserves and binds the evidence run before its final parent turn. That turn receives the exact run reference and can attach measured evidence through the existing work tools. A lost binding response is never retried. Duplicate starts only observe the existing plan, including after restart.

The runner does not approve evidence, accept a task or establish gameplay success. Its final review reference remains pending human evidence review. Original ownership and cancellation checks guard every asynchronous boundary; retained journal observations do not revive authority.

The coordinator starts eligible plans after a genuine human Send acknowledgement. Parent updates use the original client's opaque continuation chain, with at most two incorporation permits and the original account, conversation, model and grants. Plan cancellation fences this chain independently of the single repair continuation. Native work authority ends with the final active parent turn; retained provenance cannot recreate it.

Temporary SQLite, owned native peers and actual SDK/HTTP fixtures cover sequencing, restart, cancellation, uncertain acknowledgements, budgets and bound evidence authority. The desktop reads bounded display-only status and opens the exact evidence run through the human workbench. Installed inference and native Studio acceptance remain separate.
